## 1. 首分钟西部版的教训

### 1.1 实测数据

| 指标 | 数值 |
|---|---|
| 正常通关 | 59.8 秒，开 6 枪 |
| 提前命中路线 | 44.4 秒，开 6 枪 |
| 每发对应的整局时长 | 44.43 秒或 59.77 秒除以 6，约 7.4 或 10.0 秒，含序幕和转场。相邻两次交互之间的实际间隔需单独打点 |
| 威胁片段的普通有效窗口 | 马车至酒馆依次为 3.00、2.75、2.58、2.38、2.25、2.00 秒，合计约 15 秒。部分入场和过渡尾段还有提前命中窗口 |
| 同屏目标数 | 始终 1 个 |
| 弹药与目标 | 6 发对 6 个目标，完美通关不需要换弹 |
| 反馈特效 | 命中是一个 0.16 秒放大的细圆环；受伤是上下各 8 像素红条加 2.5 像素震屏 |
| 音效 | 程序合成的噪声加正弦波，每声 85–180 毫秒 |

### 1.2 试玩反馈的根因

| 反馈 | 根因 |
|---|---|
| 节奏太慢 | 开场和跨场转移占据较长时间。两条路线都只有六次命中，提前打完主要缩短了等待镜头 |
| 太简单 | 同时只有一个目标。完美路线无需换弹；教学有超时保护，末段的酒馆解救可以直接点击星徽完成 |
| 特效差 | 只用了 SDL_Renderer 的矩形、线、圆环，没有贴图特效、粒子、着色器、顿帧和武器；视频里的敌人中弹只是缩回掩体；音效是合成蜂鸣 |

### 1.3 结论

"整帧分支"把敌人画在视频里，每次交互都切换整段视频。西部版的问题不是这个结构本身，而是每个节拍串行消耗的视频段太多、每段都太长：一次交互要走完"入场 1 秒 + 等待最长 3 秒 + 反应 1.5 秒 + 转场 3 秒"，节拍之间的转场还什么也不能做。

敌人仍然要由视频模型生成：写实风格下，引擎叠加的人物和妖怪质感比不上视频生成的画面。多路局部视频拼接（分区合成）评估后放弃：接缝、多路解码和逐帧对齐都是不可靠因素。

新游戏沿用**整帧分支、同屏只有一个目标**，用"接力链"把节奏做快（第 10.2 节）：

- **净化和转场合并成一段**。当前目标消散时下一个目标在别处现身，镜头顺势微移。用首个可辨认的有效帧开放下一次交互，逐段测量等待。
- **有效命中立即有反馈**。根据命中所在的动作阶段选衔接画面；普通目标、飞行中的火球和受保护角色分别按当前显示帧处理。
- **引擎只负责 UI 和玩家实时交互的效果**：准星、开枪、命中火花、受击红屏、震屏、雷符的天雷。

另一条教训是流程上的：先生产了一分钟视频，试玩后才发现节奏和难度有问题。新游戏先做战斗原型验证好不好玩，再大量生产（第 13 节）。如果接力链验证下来还是不够快，转入第 10.9 节的"故事优先"模式，把筹码押在剧情和画面上。

## 3. 游戏概念

一句话：像看一部古装奇幻电影，同时亲手驱妖。

体验目标：

1. **好看**：长安上元夜的灯海、华美的唐装、好看的人物。
2. **好玩**：战斗一波接一波不冷场，要瞄准、要拦截、不误伤、要换符，每一枪都有华丽的反馈。
3. **动人**：剧情有悬念、有感情，结局让人记住。
4. **不吓人**：妖怪是活过来的灯、纸、器物和灵体；被打中后是"净化"，不是死亡。

## 4. 故事

### 4.1 设定

大唐长安，上元节，三夜不禁夜，十万盏灯点亮全城。

镇妖司是朝廷里专管妖事的衙门，执灯使手持符弩，以符箭净化作乱的妖灵。今年上元夜，灯里沉睡的灯妖一齐苏醒。

### 4.2 人物

| 角色 | 身份 | 形象 | 性格 | 配音 |
|---|---|---|---|---|
| 沈砚 | 玩家。镇妖司新任执灯使，二十岁 | 英俊少年，玄青色窄袖官服，束发，背负符弩 | 沉稳少言，外冷内热 | 年轻男声，克制 |
| 阿萤 | 女主。萤火灯笼化成的灯妖，外表十七八岁 | 灵动漂亮，暖金和浅杏色的唐装襦裙，发间别一盏小灯，身边绕着萤火 | 活泼、好奇、心软；她自己也不知道自己从哪里来 | 少女声，明亮，情感起伏大 |
| 裴照 | 镇妖司司丞，沈砚的上司和师父，三十岁 | 冷艳的女剑客，银白软甲外罩白色披风，佩横刀 | 严厉、果决，私下护短 | 成熟女声，冷 |
| 玄烛 | 反派，人称"夜行公子"，千年灯魔 | 白衣美男，长发半束，手持一盏青灯，青色鬼火绕身 | 温柔、优雅、悲伤，执念极深 | 低沉男声，温柔而危险 |
| 旁白 | — | — | — | 沉稳的男声或女声 |

### 4.3 主线

一千年前，玄烛是长安最好的灯匠。他为病中的妻子做了一盏萤火灯，承诺上元节带她看灯。妻子没能等到那一夜。他守着那盏灯不肯放手，悲痛和执念让他成了灯魔。

一千年后，他要借十万盏灯打开"万灯鬼门"，把亡妻的魂魄从另一边带回来。可鬼门一开，长安的活人也会被拖进去。

他不知道的是，那盏萤火灯在千年里生出了自己的灵，就是阿萤。

结局：沈砚射碎玄烛心中的灯芯。玄烛在光里看见了妻子，含笑消散。阿萤为了助沈砚射出这一箭，耗尽了自己的灵力。她的身体在晨光里一点点变得透明，最后对沈砚说："沈大人，明年的上元节……替我看灯。"然后化作满天萤火，在天亮之前散尽。她没有回来。

尾声：一年后的上元夜，长安又点起十万盏灯。沈砚独自站在城楼上，手里提着那盏已经熄灭的萤火灯。他把灯挂在檐下点亮，灯里没有萤火。他望着灯海，轻声说："今年的灯，很好看。"

玄烛当年答应带妻子看灯，没有做到；阿萤托沈砚替她看灯，他做到了。两条线在结尾形成对照，伤感但不绝望。

## 5. 玩法

### 5.1 核心循环

```
CG（剧情）→ 战斗（一波接一波的妖灵）→ 剧情一枪 / 短过场 → 战斗 → Boss → CG（结尾，留下钩子）
```

- CG 集中成段播放，可以按段跳过。
- 战斗段里不插入超过 3 秒的不可操作画面。

### 5.2 操作

| 动作 | 鼠标 | TVGun |
|---|---|---|
| 射击 | 左键 | 扳机（点手机屏幕） |
| 换符匣 | 右键 | 向屏幕外射击，或 RELOAD 键 |
| 雷符 | 中键或空格 | 新增的雷符键（第 10.7 节） |
| 跳过 CG | 空格（CG 中） | START 键 |
| 暂停 | Esc | 失锁自动暂停 |

### 5.3 符弩

- 一匣 8 支符箭，普通难度换符匣用时 0.6 秒，其他难度见 §5.9。
- 鼠标模式在屏幕右下角显示符弩；开枪时弩身后坐，弩口迸出符光。TVGun 模式默认不显示。
- 没有射速限制，但每一箭都有完整的开火反馈。

### 5.4 雷符（大招）

| 项 | 规则 |
|---|---|
| 充能 | 玩家每次有效符箭命中 +1 格。按难度满 15 / 20 / 25 格可用，最多储存一次 |
| 扣减 | 有效开火窗口打空 −2 格，最低为零。受伤清零 |
| 释放 | 对当前可净化的小妖直接净化，对可受击的精英造成 2 点伤害。Boss 仅在带有专用暴露分支的阶段可用，进入 3 秒的符印暴露窗口。成功释放消耗满槽，净化照给分，雷符自身不充能、不累加连击 |
| 限制 | 纯转场、拦截火球、保护对象和普通 CG / 剧情一枪期间锁定战斗雷符，保留能量 |
| 第 5 章 | 终章强制充满的是剧情雷符。屏幕提示玩家按普通射击键击碎灯芯，使用独立剧情窗口和演出，不占战斗雷符输入 |

M0 与正式版默认采用单目标雷符。若后续选做三连净化，需要另做连续三节点的专用短片，先验证完整时长、节点切换和末尾不足三个目标的处理，再排入生产。

### 5.5 妖怪

设计原则：

- 写实画面里，最不吓人的是"活过来的器物"和灵体，再加上漂亮的人形妖（狐火少女）。净化后的样子要让玩家觉得"救了它"。
- 每个目标单独占一段视频，同屏只有一个可射击目标（第 10.2 节），所以妖怪在片段里可以自由动作（扑、飞、喷吐、横穿画面）；但一个动作必须在一段片段内完成，或经锚帧切换到下一段。
- 妖怪一现身就要有威胁感：出场即蓄力，不做"亮相、待机、才想起攻击"的拖沓。
- 每种妖怪都要有清楚的蓄力动作，玩家看得出它要攻击了。

**小妖**（一箭净化，接力出现，一波里多个依次上阵）

| 妖怪 | 出现章节 | 行为 | 净化后 |
|---|---|---|---|
| 纸灯笼妖 | 1、2、5 | 从摊位或屋檐下飘起，眼睛亮起后扑向镜头 | 灯纸散成光点，灯笼落地熄灭 |
| 鬼火 | 1、3、5 | 在原地聚成一团，变亮后冲向镜头 | 化成萤光消散 |
| 纸鹤妖 | 2、4 | 从纸堆里折成形，在原地盘旋后扑向镜头 | 恢复成普通纸鹤落下 |
| 墨鸦 | 4 | 从经卷堆里飞起，张翅后向镜头俯冲 | 散成墨点，落在经卷上成字 |
| 河灯妖 | 3 | 从水面浮起，吐出鬼火球 | 莲花河灯重新浮在水面 |

**精英妖**（2–4 箭，有蓄力和攻击动作）

### 5.7 判定

- 按开枪时刻正在显示的那一帧判定，沿用西部版的显示帧记录。
- 普通接力按当前片段、显示帧和节点查掩码；镜廊、护灯等同屏多区域事件另带区域 ID。火球飞行、举盾和现形各有自己的生效区间，见 §10.4。
- 掩码逐帧生成：目标在片段内移动时，优先用与参照帧的差异自动提取，辅以人工框选和 SAM2（妖怪和光、烟重叠时差异法不准）；弱点、盾牌、百姓和阿萤的子区域另外标注。
- 每帧先选择当前玩法阶段，再查可见表面掩码。拦截窗口仅开放火球，举盾时盾面返回跳弹，照妖从现形帧开放。遮挡处按最前可见表面标注，保护对象的可见轮廓排除辅助扩张。同一输入只结算一种结果。
- 辅助瞄准只在妖怪轮廓外的窄带内生效，避开百姓和阿萤；扩张量按难度配置（第 5.9 节）。

## 7. 节奏和难度硬指标

每次普通接力用同一单调时钟记三个时间，附带节点、片段、显示帧、难度和输入来源。T_hit 是令上一节点净化的那次命中时间，T_open 是下一目标有效掩码首次显示的时间（可能在接力片尾段），T_input 是玩家向下一目标发出首个有效射击输入的时间。分别报告系统等待 T_open−T_hit 和玩家反应 T_input−T_open。每条样本保留实值；暂停、重试和跨场路线单列。顿帧算进系统等待。自动回放可验证时序，真人试玩用于判断能否看懂，以及是否愿意接着玩。

| 阶段 | 验收项目 | 记录与判定 |
|---|---|---|
| 三节点小样 M0-A0 | 两次普通接力 | 设计区间 1.2–1.8 秒，每条样本最多 2 秒。提前开放可短于 1.2 秒，须由试玩确认下一目标看得清。剪点早、中、晚均可接受；转场抢打能正确结算 |
| M0-A0 | 火球与精英 | 分别回放末个有效帧拦截、未拦截抵达、精英受击恢复与最终净化。生命、血量和分数在每次事件中只结算一次 |
| 12 节点原型 M0-A1 | 节奏、难度与弹量 | 三档各走通；普通难度的完整正常路线至少需要换匣一次。记录预警开始、发射、拦截及抵达次数。普通预警的设计范围为 1.0–1.8 秒，跨场不可操作片段最多 2 秒 |
| 完整章节 M1 起 | 换符、攻击机会与变化 | 按普通路线列出每章所需有效箭数、初始弹量、补给与雷符消费。每章 6 次换符、15 次可读预警作为调参目标。8 支满匣起步、无额外补给时，第 49 支才使第 6 次换符成为必需。分别统计预警出现、玩家提前打断、攻击实际抵达；每章安排至少一个新妖怪和一个新机制 |

未达接力标准时先定位到具体动作或剪点，试 §10.2 的局部修正并重测。仍超时或出现明显跳位，带同一段素材的对照回放进入 §10.9 评审。

## 9. 美术

### 9.1 风格

写实古装电影的质感，参考《妖猫传》《长安十二时辰》的唐代美术，以及夜景灯光的电影摄影。

- 全游戏是夜景，以暖色灯光（花灯、烛火）为主，冷色月光和青色鬼火做对比。
- 电影调色（LUT）和胶片颗粒统一视频及场内特效的质感。字幕、操作提示和 TVGun 定位白框在后处理之后绘制，暗场与白闪期间也保持清晰。
- 夜景暗部多、灯光本身在闪烁，片段衔接处的细微差异更不易被察觉，这也是选择上元夜的原因之一。

### 9.2 人物

- 4 个具名角色各做一套定妆照：正面、3/4 侧面、全身、脸部特写，加 2–3 张不同光照下的样张。
- 人物要好看：五官、身材、服装都按古装电影的主角标准。阿萤的服装颜色要和场景灯光呼应。
- 服装和发型有醒目、固定的特征（沈砚的玄青官服和背上的符弩；阿萤发间的小灯和身边的萤火；裴照的白披风；玄烛的白衣和青灯），在远景和侧面镜头里也能认出来。

### 9.3 妖怪

- 器物和灵体为主，不做血肉、骨骼、伤口、腐烂这类内容。
- 都会发光，颜色和场景灯光呼应：灯笼妖暖橙，鬼火青蓝，狐火粉白，玄烛的火青绿。
- 有"表情"：灯笼妖的眼睛圆而灵活，狐火少女戴面具，皮影武士有夸张的戏曲姿态。
- 可爱和华丽多于恐怖，适合全年龄。

### 9.4 写实风格下的一致性

写实人脸是本项目最大的生产风险，按下面的办法逐层控制：

1. **镜头设计**：CG 以中景和全景为主，脸部大特写只用在最关键的情感镜头（预计全游戏不超过 15 个）。
2. **锚帧**：每个 CG 镜头的首帧都用"定妆照加场景"编辑出来，经人工确认后才生成视频。
3. **参考图**：H3 生成时用 ReferenceToVideo 带上定妆照（与首帧锚定能否同时生效，M0 验证）。
4. **角色 LoRA**：如果前三步锁不住，就为 4 个具名角色各训练一个出图 LoRA。
5. **人工把关**：每个镜头挑选时，和定妆照并排对比。

## 10. 技术方案

### 10.1 画面分层

```
UI（HUD、字幕、雷符槽、蓄力光环、TVGun 白边）
后处理（LUT 调色、暗角、色差、胶片颗粒）
玩家交互特效（开枪、命中火花、受击叠层、天雷）
整帧视频（战斗片段、接力转场、CG、Boss 大场面）
```

引擎不绘制任何角色。人物、妖怪、百姓、阿萤都在视频层里。

### 10.2 整帧分支加速：接力链

**战斗段（chain）**：一个接一个的目标，每个目标是整帧视频里唯一可射击的敌人。西部版"慢"不是因为整帧分支，而是因为每个节拍要串行消耗太多段视频；这里把节拍压缩成两段片段：威胁和净化转场。

**片段种类**（每个目标节点）：

| 片段 | 首帧 → 尾帧 | 内容 | 时长 |
|---|---|---|---|
| `threat` | K → K | 目标现身即蓄力，蓄力满则开火或扑击，再回到蓄力循环 | 1.5–3 秒 |
| `purify_next` | K_hit → K_next | 当前妖灵消散，镜头微移，下一目标在尾段现身；尾段可提前命中 | 1.2–1.8 秒 |
| `purify_end` | K_hit → 下一段入点 | 链末目标净化，汇入 CG、下一场或结算 | 按段定稿 |
| `flinch` | K_hit → K | 精英妖受击硬直后恢复（多箭目标才需要） | 0.5–0.8 秒 |
| `interrupt` | 攻击中段 → K | 投射物被打碎、扑击被弹回，回到蓄力 | 0.6–1 秒 |
| `scare` | K_civ → P | 误伤百姓或阿萤的后果反应 | 1–2 秒 |

K 是目标就绪锚帧，K_hit 是受击入口锚帧，K_next 是下一节点就绪锚帧，K_civ 是百姓在场面的锚帧。同一节点可为不同动作区间指定不同的 K_hit。

**规则**：

- 在当前节点的有效帧内命中后，以实际显示帧和动作区间选择受击入口。小妖及耐久归零的精英走净化，尚有耐久的精英走 `flinch`。普通接力走 `purify_next`，链尾走 `purify_end`。顿帧按 §8 执行。
- `purify_next` 的尾帧和下一段 `threat` 的首帧共用 K_next；从转场中下一目标首次清楚可辨且可击中的帧起，掩码属于下一节点，提前命中直接进入该节点的受击分支。正常过片保留同一目标的耐久、连击和结算状态。
- 没有互动对象的纯转场忽略射击，弹药、命中率、连击和雷符能量均保持。此类转场可以换匣；两场之间的镜头目标长度为 1.5–2 秒。
- 投射物将“发射”“可拦截”“抵达”分别标帧。发射产生火球，飞行窗口开放火球掩码，抵达前最后一个可拦截帧的有效输入仍能取消伤害。未拦截才在抵达帧扣命。无投射物的扑击按实际接触帧扣命。同一轮最多扣一次，生命归零优先进入失败分支。
- 切片、重试和续关后，来自旧节点或旧轮次的迟到输入丢弃；转场和下一段共用的可击区间按同一目标去重。

**受击入口选取。** 先用一张场面母版和每节点一对 K、K_hit 试拍。针对移动目标，在有效窗口的早、中、晚各命中一次，并覆盖上一条接力片的提前命中。对照命中前的实际显示帧与受击首帧的主体位置、大小、姿势和背景。入口通用时共用一个锚帧；个别区间跳位时，先收敛动作，再为仍有问题的区间取成片姿态制作额外入口。

朱雀大街的战斗机位固定。M0 为整场遭遇共用一段 H3 街景。入场时行人走近摊位，约 7.3 秒后停在末帧。威胁循环、受击和拦截只切换前景表演，暂停同时冻结街景和怪物。新开局从街景首帧起播。前景按全画幅保留妖怪、火花与石板反光，游戏按逻辑帧的独立蒙版判定命中。验收要覆盖原地等到怪物再次攻击，以及命中后立即换匣。[试玩验收](CHANGAN_STREET_ONCE_QA.md)

**生成（H3）**：`threat` 用 K 做首尾帧锚定；`purify_next` 用 K_hit 锚首帧、K_next 锚尾帧，提示词写明"前者消散成光点、镜头微微移动、后者在某处现身"。

**复用**：一个场面设 4–6 个出场位置轮换（摊位、屋檐、牌楼、车顶、水面）、2 套阵容（例如先是灯笼妖，后是狐火少女加灯笼妖）。位置重复出现时换妖怪种类和动作，锚帧另做。`purify_next` 只生成编排用到的相邻配对，不做全排列。

**约束**：

- 目标在自己的片段里可以自由动作（扑、飞、喷吐、横穿画面）；但一个动作必须在一段片段内完成，或经锚帧切换到下一段。
- 接力转场里"下一个目标的现身"要短（不超过 0.6 秒）且位置明确，让玩家一眼找到下一个目标。
- 蓄力、开火、净化这些关键时刻必须落在可标注掩码的清晰姿势上。

**转场兜底。** 双动作转场若出现明显穿帮，先试 0.8–1.2 秒的短净化，再切到下一目标出场。登记需要补拍的短净化和出场边，按 §7 实测命中到下一目标首个可击帧的间隔，再按 §13 决定是否扩产。

### 10.3 解码与性能

西部首分钟启动时遍历所有切片，逐个校验哈希、创建 `Movie` 并预解首帧，各片段的压缩视频包和解出的音频保留在内存。现有解码校验和纹理尺寸固定为 1280×720。长安要实现按需载入；支持 1080p 时须让解码、纹理及掩码坐标共用素材清单中的尺寸。西部的分支判定与显示帧记录可以复用。现状见[播放器启动逻辑](../apps/player/main.cpp)和[解码实现](../apps/player/media.cpp)。

| 平台 | 解码 |
|---|---|
| PC | M0 用 FFmpeg 软解 720p 跑通，保存分辨率和性能记录，再按发行目标复测 1080p |
| Android（2015 年主流芯片） | 计划用 MediaCodec 硬解当前片段。预热深度、是否能并行软解或硬解，由目标真机决定 |

- 进入节点时按当前血量、画面阶段和后继边确定要预热的片段。普通节点优先预热净化，精英未到最后一次命中优先预热硬直，火球飞行时优先预热拦截。预算不足的分支收到事件即加载。等首帧就绪后一次切换画面、音轨与判定代次，等待期间冻结旧片判定，避免重复扣血或计分。
- 运行期间只保留当前片段和配置允许的后继工作集。节点离开、跳段、续关或退出时淘汰无引用的压缩包、解码器、音频、前缀帧和纹理，丢弃上一次加载请求的迟到结果。生产校验遍历整章，运行时按清单核对实际载入的素材。
- 前缀缓存以实测字节设上限。以 8 位 YUV420 紧密排列估算，720p 的 8/12 帧约占 10.5/15.8 MiB，1080p 约占 23.7/35.6 MiB。这是单份像素数据，另计对齐、解码器表面、压缩包、PCM 和 GPU 纹理。缓存存在哪一侧就在哪一侧计账，双份驻留分别计入。
- M0 记录首帧等待时间、分支输入到反馈提交及分支首帧提交的 P50/P95 和样本数，区分预热命中和未命中。重复跨场景切换、续关和返回标题，记录同时存活的解码器数、进程内存峰值、缓存字节与 GPU 纹理分配，检查是否随走过的节点持续增长。手机到电视显示的延迟单列实机测量。

### 10.4 遭遇时间轴

战斗段由数据驱动，一条接力链是一串目标节点：

```yaml
# worlds/changan/ch1/chain_02.yaml（示意）
arena: ch1_street_b            # 场面：空镜母版、出场位置集合、场面转场
chain:
  - { monster: lantern,  spot: stall_left }
  - { monster: lantern,  spot: roof_right }
  - { monster: wisp,     spot: eave_mid,   voice: { who: ayin, line: "右边屋檐！" } }
  - { monster: lantern,  spot: cart_right, decoy: civilian_cross }
  - { monster: fox_girl, spot: eave_mid,   hp: 3 }          # 精英：flinch 后回 threat
  - { monster: wisp,     spot: stall_left, projectile: fireball }
```

- 编排节点顺序后，为每条实际分支登记源片、结果、目标片或终点、入口锚帧及恢复位置。包括链尾、诱饵跳过、误伤与恢复、受击、拦截和三档难度。镜廊记录两面假镜各自是否已碎，若允许任意顺序，两种首击各有对应画面。
- `decoy` 对带百姓的成片启用保护掩码。误伤按难度结算，仍有生命时播 `scare` 并从明确的恢复点接回，生命归零直接转失败。
- `projectile` 节点给出 `launch_frame`、拦截区间和 `impact_frame`。发射帧不晚于拦截起帧，拦截末界不晚于抵达帧。火球已在视频中，互动掩码和反馈与其共用显示帧。
- 源帧从 0 编号，窗口统一为左闭右开区间；每个区间关联最终成片哈希、所属节点、可见掩码和受击入口。精英受击立即扣除本次耐久，恢复片结束时沿用剩余耐久。
- `threat` 与接力尾段均标首个可击中帧；按机制另标现形、举盾/收盾、扑击或投射物窗口。逐条重放窗口首帧、末个有效帧和失效后的首帧。
- 语音和字幕事件挂在节点上；波次之间插整帧场面转场。
- 难度参数在运行时应用（第 5.9 节）：起播偏移、诱饵节点是否启用、精英 hp、窗口倍率。
- 开发模式下可视化：节点列表、跳转、掩码和窗口帧检查。

### 10.6 剧情一枪

- CG 片段在关键时刻停在一个"慢动作段"上：H3 单独生成一段慢动作片段，或者引擎对原片做帧保持加慢放。
- 屏幕上出现目标提示（金色光圈），窗口时长按难度配置。
- 命中：顿帧、符光、播放"成功"短片。失手或超时：播放"失手"短片，例如符箭射偏，阿萤自己挣断了绳子。两段短片的末帧都是同一个锚帧，汇合后剧情继续。
- 剧情一枪只影响得分，两条结果汇入同一主线。终章借力后提示按普通射击键施放剧情雷符，命中与失手均进入鬼门关闭的结局，失手或超时由阿萤补全符力。镜廊的两面假镜按 §10.4 的状态记录分别处理。

### 10.7 TVGun 的改动

- 手机端新增"雷符"虚拟按键，UDP 新增 `SPECIAL` 事件，HTTP 新增 `/special`。
- 手机端在游戏模式下，可选把音量下键映射为雷符（音量键目前用于录制和切换镜头，只在游戏模式下改）。
- 引擎在 START 键上增加"跳过 CG"的功能。
- 修改 `D:\tvgun\android`，放在 M2 完成。

### 10.9 兜底：故事优先模式

如果 M0-A 的局部修正仍达不到 §7 的指标，交付同一场景的接力版和短净化版回放，并列出耗时和失败剪点。需求方试玩后选择继续修接力，或选用以下故事优先方案。确定模式后再更新章节排程与素材清单。

- 战斗退化为独立的单节拍：每个目标用自己的"入场 → 蓄力 → 净化"三段式（类似西部版，但片段剪短、动作前置），目标间隔放宽到约 4–6 秒。
- 战斗占比下调：CG 从约 35% 提到约 45%；战斗段数减少、每段目标数减少，省下的生成量投入 CG、附身、辨真和 Boss 的质量。
- 第 7 节指标重估：只保留和手感相关的（窗口按章缩短、有诱饵、要拦截、要换符），不再考核开枪频率。
- 打击感规格（第 8 节）不变：即使节奏慢，每一枪的反馈必须到位。
- 剧情一枪和 Boss 大场面不变，它们本来就是本方案的强项。

## 11. 生产管线

### 11.1 CG

1. 按章节写分镜脚本：每个镜头的景别、机位、人物、动作、台词、时长。
2. 每个镜头一张首帧关键帧（ChatGPT 出图，用定妆照和场景母版作参考），需要时加一张尾帧。
3. 台词先用 TTS 生成（每个角色一段参考音频做声音克隆），再用 H3 的 AddGuide 音频锚定生成口型。
4. 用 H3 生成视频，每个镜头 3 个候选，挑选最好的。
5. 剪辑成段，校色，与配音和环境声混音，加字幕时间轴。

### 11.2 战斗接力链

1. 先画状态图，给每条可达边记起点、触发条件、离开时画面、终点、接续锚帧与片段 ID；标出待生成或已有素材及复用依据。同一段用于不同边时，分别核对画面里的角色、位置和道具状态。每条链都要登记最后一次净化如何进入下一场、CG 或结算。
2. 场景母版规划 4–6 个可轮换的出场位置。母版、角色定妆、妖怪设定与节点锚帧均有稳定 ID。锚帧登记所用母版、角色参考图及其版本。先制作三节点样片所用的锚帧，移动目标的受击接片入口按 §10.2 的早、中、晚实测补齐。
3. H3 生成时将 `threat` 的首尾锚和每条转场的出入锚连同工作流版本写入生产清单。普通相邻边可用 `purify_next`。末节点准备净化收尾，跨场面按需要生成 1.5–2 秒镜头移动。硬直、拦截、受惊恢复，以及按难度绕过诱饵的边分别检查能否复用。
4. 定稿文件保留无 UI 的视频，登记文件哈希、帧数、帧率和候选来源。按实际定稿帧审核两端接缝及窗口内的早、中、晚命中；为跨片提前命中同时标注转场尾段。蓄力、发射、拦截、伤害及子区域掩码与定稿文件的哈希绑定。素材换版后复核所有引用这段片的边。

### 11.3 妖怪设定

- 每种妖怪一张设定图（ChatGPT 出图）：正面、侧面、蓄力姿势、攻击姿势，加上净化后的样子。
- 阵容锚帧里的妖怪都按设定图编辑，保证同一种妖怪在不同场面里样子一致。

### 11.4 Boss、附身、辨真

- 按西部版的状态图方式做：关键帧、首尾帧锚定的整帧片段、掩码标注。
- Boss 身上可以独立反应的部位（九首龙舟灯的九个龙头、护灯）用同一帧内的局部掩码判定，部位本身仍画在整帧视频里。
- 镜廊允许先打任一面假镜。台账要有“只碎左镜”和“只碎右镜”两种画面，再汇合至两面已碎；已经碎掉的镜面退出判定。Boss 按可见状态列护灯熄灭、阶段切换、打错恢复与最终收尾所需的素材。

### 11.6 生产量估算

以下是按原方案估算的制作规模。立项工期以状态图和首批实际生产记录重算。

| 项 | 初估规模及复算依据 |
|---|---|
| 定妆照和角色设定图 | 4 个具名角色，每人约 6 张 |
| 场景母版 | 约 25 张 |
| CG 镜头 | 约 120 个（平均 3 秒），每个 3 个候选，约 360 次生成 |
| 战斗接力链 | 原估 10 条链、145 个节点，对应 145 段威胁和 135 条链内相邻边。另登记 10 次链尾净化及去向，逐边核对能否复用。原估约 50 段补充片、约 850 次生成和约 300 张目标锚帧，需纳入移动目标的受击入口、转场抢先命中、诱饵绕行及失败恢复后重算 |
| Boss 片段 | 5 个 Boss，每个约 8 段，约 40 段；每段 3 个候选，约 120 次生成 |
| 附身、辨真 | 约 15 段整帧片段，每段 3 个候选，约 45 次生成 |
| 视频生成合计 | 旧估约 1,375 次（含候选）。按去重后的待生成片段 ID、各类片段的候选数和实测返工率复算 |
| 配音 | 约 150 句剧情台词，加约 80 句战斗喊话 |

M0 开始即按片段类型记录候选数、通过数、未通过原因、总 GPU 分钟和人工挑选/标注时间。候选通过率 = 通过候选数 ÷ 完成审核的候选数；单位定稿成本 = 该类全部候选（含失败尝试）的 GPU 分钟 ÷ 定稿片段数。样本为零的类型标为待测。每章开工前按新增独立片段数换算所需 GPU 小时，并把人工工时分列；H3、出图和声音共用 GPU 时同列入排期。

|---|---|---|
| 主题曲 | 标题画面、宣传 | 1 |

## 14. 主要风险

| # | 风险 | 缓解 |
|---|---|---|
| 1 | 写实人脸在大量 CG 镜头里保持好看和一致 | 第 9.4 节的五层控制；M0-B 先验证；必要时训练角色 LoRA |

## 16. 模型与环境

### 16.1 原则

- 本地 H3、TTS、音乐备选及掩码工具在 WSL（Ubuntu-22.04）里运行；ChatGPT 出图及 Mureka 音乐按各自服务工作流执行。引擎在 Windows 上构建和运行。
- 只有一块 RTX 5090（32GB）。H3 运行时几乎占满显存，所有 GPU 任务都通过同一个文件锁排队（沿用 SoundGame 的做法：`flock ~/.gpu.lock <命令>`）。白天跑出图、配音、音乐、掩码这类短任务，夜里批量跑 H3。
- 本机连不上 huggingface.co，下载一律设置 `HF_ENDPOINT=https://hf-mirror.com`（SoundGame 已验证）。需要授权的模型（gated）要带 HuggingFace token。
- 视频和出图只用 `~/aivideo/ComfyUI` 一个实例，`tools/forge` 通过它的 HTTP API 提交任务。它已通过 `extra_model_paths.yaml` 挂载了 `~/ComfyUI/models` 里的出图模型。
- 对齐、掩码、衔接检查、响度处理这些非 ComfyUI 的步骤，用 `tools/forge` 自己的 Python 环境执行，不往 ComfyUI 里加自定义节点。
- 密钥（Mureka API key、HF token）放在 `~/.config/reelgun/*.env`，不进仓库。
